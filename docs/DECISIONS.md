# 설계 결정 기록

## 1. 문서 규칙

- 이 문서는 0단계에서 합의한 설계 기준과 아직 확정되지 않은 운영 입력을 분리한다.
- `확정`은 구현 기준, `개발 기본값`은 Emulator·개발·부하 시험용 초기안, `미결정`은 외부 확인 전 운영에 적용할 수 없는 값이다.
- 개발 기본값은 모든 동아리에 동일하게 적용한다. 운영값을 바꿀 때는 `market/config` 한 곳, 관련 계약 문서, 테스트 기대값을 함께 바꾸고 감사 가능한 변경 기록을 남긴다.
- 미결정 사항을 코드나 시드에서 임의로 채우지 않는다. 자리표시자는 그대로 유지하고, 누락 시 운영 배포를 실패시키는 사전 점검을 둔다.

## 3. 공정한 시장 개발 기본값

아래 값은 개발·Emulator·부하 시험의 보수적 초기안이다. 모든 22개 종목에 동일하게 적용하며 축제 운영 전 승인과 부하 시험을 거쳐 조정할 수 있다.

| 설정 | 개발 기본값 | 선택 이유 |
| --- | ---: | --- |
| `initialPrice`, `basePrice`, `previousClose` | 10,000원 | 학생이 100만원으로 수량과 평가액을 직관적으로 이해할 수 있고 원 단위 계산이 단순하다. |
| `issuedShares` | 100,000주 | 모든 종목의 명목 규모를 같게 하고 수백 명 규모 시험에 충분한 보수적 기준을 제공한다. 실제 재고 제약 의미는 미결정 항목 U-008에서 확정한다. |
| 초기 `marketCap` | 1,000,000,000원 | `initialPrice × issuedShares`의 파생값이며 종목 간 완전히 동일하다. |
| 초기 `buyVolume`, `sellVolume`, `totalVolume` | 0주 | 사전 인기 편향을 만들지 않는다. |
| 초기 별점 | 평균 3.0, 평가 수 0, 최근 변화 0, `lastRatingAt=null` | 외부 별점이 없을 때 가격에 중립이다. UI는 평가 수 0을 '평가 없음'으로 표시하고 엔진은 3.0으로 수축한다. |
| 별점 사전분포 | 평균 3.0, 가중치 20건 | 소수 평가의 급격한 영향을 완화한다. 운영 데이터로 민감도 검증 후 바꿀 수 있다. |
| 별점 수준/최근 변화 가중치 | 700/300 permille | 절대 수준을 주 신호로 두되 최근 변화도 제한적으로 반영하며 합을 1,000으로 고정한다. |
| 별점 정규화 폭 | 수준 2,000 milli-star, 최근 변화 1,000 milli-star | 1~5점 척도와 최근 ±1.0점 변화를 정수 ppm 신호로 변환한다. |
| 별점 freshness 개발안 | 10분까지 유지, 10~30분 선형 감쇠, 30분에 최근 기여 0 | 공급자 지연이 즉시 급변을 만들지 않게 하며 오래된 최근 변화가 계속 가격에 영향을 주지 않게 한다. 운영 전 API SLA로 승인한다. |
| `minPrice` | 100원 | 0원·음수를 원천 차단하면서 가격 변화를 관찰할 공간을 둔다. |
| 수요 샤드 수 | 10 | 수백 명 규모의 인기 종목 집중을 분산하면서 tick당 읽기 수를 제한한다. |
| 수요 유동성 바닥 | 100주 | 한두 주의 단독 거래가 수요 기여 상한을 즉시 만들지 않게 한다. |
| 수요 윈도우/가격 목표 주기 | 60초 | Cloud Scheduler의 분 단위 실행 모델과 비용·안정성을 고려한 구현 가능한 기준이다. |
| 가격 최대 허용 지연 | 120초 | 일시적 재시도 한 번을 허용하되 UI가 장애로 판단할 명확한 상한을 둔다. |
| 별점 target premium 상한 | ±50bp | 저표본 평가의 가격 지배와 반복 복리를 막는다. |
| 별점 최신성 감쇠 | 10분까지 전량, 10~30분 선형 감쇠, 30분 이후 0 | 오래된 최근 변화가 가격을 계속 움직이지 않게 하는 개발 기준이다. 공급자 계약 확인 후 공통 조정한다. |
| 수요 fundamental 이동 상한 | tick당 ±120bp | 거래가 주된 영구 가격 신호가 되되 과열을 제한한다. |
| 활성 관리자 target premium 합산 상한 | ±60bp | 호재·악재를 절대 target으로 적용해 반복 복리를 막고 자의적 영향을 제한한다. |
| 현재가 tick 이동 상한 | ±200bp(±2.00%) | fundamental과 target premium이 만든 목표가를 향해 한 번에 과도하게 움직이지 않게 한다. |
| 반올림 | 평균·신호는 half-up, 상한이 있는 가격 delta는 toward-zero | 결정론을 유지하면서 낮은 정수 가격에서도 설정한 bp 상한을 초과하지 않는다. |
| 랭킹 목표 주기 / 최대 지연 | 60초 / 120초 | 실시간 체감을 유지하면서 전체 사용자 평가 비용과 경합을 제한한다. |

계수 단위는 basis point(`1bp = 0.01%`)로 저장한다. 수요는 정수 `fundamentalPrice`를 이동시키고 별점·관리자는 그 기준에 붙는 절대 target premium으로 계산한다. 현재가는 target을 향해 tick당 ±200bp 안에서 움직이며 모든 설정 버전과 입력 해시를 기록한다.

## 4. 미결정 및 운영 전 확인 항목

### U-001 학교 Google 계정 도메인

- 항목: 허용할 실제 학교 이메일 도메인
- 선택지: 단일 도메인 / 복수 도메인 목록 / 학생 명부와 도메인 병행
- 권장안: 운영 초기에는 학교가 확인한 단일 도메인을 `ALLOWED_SCHOOL_DOMAIN` 서버 설정 한 곳에 넣고, 복수 도메인이 필요하면 검증된 목록형 설정으로 확장한다.
- 권장 이유: 가장 단순한 최소 권한 경계이며 코드 여러 곳의 하드코딩을 피한다.
- 변경 영향: Authentication 허용 흐름, 사용자 초기화 Function, Rules 보조 조건, E2E 계정, 운영 안내가 바뀐다.
- 운영 전 확정 필요 여부: 예. 자리표시자 상태에서는 운영 로그인과 배포를 금지한다.

### U-002 관리자 신원과 권한 부여 절차

- 항목: 관리자 이메일, 역할, custom claim 발급·회수 담당자
- 선택지: 단일 최고 관리자 / 역할 분리된 복수 관리자 / 학교 IdP·명부 기반 자동 부여
- 권장안: 최소 2명의 실명 책임자를 `market-operator`와 `incident-admin`으로 분리하고, 승인 도구가 role claim과 `adminAuthorizations`의 claimVersion을 함께 발급·회수한다. 고위험 작업은 `adminApprovals`에서 서로 다른 2인을 확인한다.
- 권장 이유: 공유 계정을 피하고 시장 초기화·복구 같은 고위험 작업에 이중 확인을 적용할 수 있다.
- 변경 영향: 관리자 UI, 서버 권한 검사, IAM, 감사 로그, 사고 대응 연락망이 바뀐다.
- 운영 전 확정 필요 여부: 예.

### U-003 축제 일정과 시간대

- 항목: 축제 날짜, 개장 시각, 폐장 시각, `FESTIVAL_TIMEZONE`
- 선택지: 운영자가 수동 개폐 / 설정된 시각에 자동 전환 / 자동 전환 후 운영자 승인
- 권장안: IANA 시간대와 서버 시각으로 사전 설정하되 개장·폐장은 운영자 2인 확인을 거치는 명시적 작업으로 한다.
- 권장 이유: 기기 시계와 시간대 오류를 피하고 현장 일정 변경에 안전하게 대응한다.
- 변경 영향: `market/state`, 거래 허용 검사, 이벤트 유효기간, 가격 tick, 폐장 스냅샷, 안내 문구가 바뀐다.
- 운영 전 확정 필요 여부: 예.

### U-004 Firebase 프로젝트, 결제, 리전

- 항목: 개발·스테이징·운영 프로젝트 ID, Blaze 결제 계정, Firestore 위치와 Functions 리전
- 선택지: 단일 프로젝트 / 개발·운영 2개 / 개발·스테이징·운영 3개
- 권장안: 3개 프로젝트를 분리하고 Firestore와 Functions를 사용자와 가까운 동일 권역에 둔다. 실제 리전은 서비스 지원 여부·학교 정책을 확인한 뒤 리소스 생성 전에 확정한다.
- 권장 이유: 운영 데이터 오염과 실수 배포를 방지하고 지연·리전 간 비용을 줄인다. Firestore 위치는 생성 후 변경하기 어렵다.
- 변경 영향: Firebase 설정, IAM, Secret Manager, Hosting 도메인, 백업 버킷, CI 배포 대상이 바뀐다.
- 운영 전 확정 필요 여부: 예.

### U-005 운영 도메인과 App Check 공급자

- 항목: Hosting 커스텀 도메인, Auth authorized domain, App Check 공급자와 enforcement 시점
- 선택지: Firebase 기본 도메인 / 학교 커스텀 도메인, reCAPTCHA 계열 공급자 선택, 처음부터 enforce / 모니터 후 enforce

- 권장 이유: 무단 스크립트 호출을 줄이되 잘못된 설정으로 전교생을 차단하는 위험을 낮춘다.

## 5. 변경 통제

결정을 바꿀 때는 다음을 한 작업으로 처리한다.

1. 이 문서의 ID, 상태, 이유와 날짜를 갱신한다.
2. 관련 제품·아키텍처·스키마·보안·가격·운영 문서를 함께 갱신한다.
3. 설정 스키마와 회귀 테스트 기대값을 갱신한다.
4. Emulator와 스테이징에서 재검증한다.
5. 운영값 변경은 승인자, 이전값, 새 값, 적용 시각, 롤백 조건을 감사 로그에 남긴다.
