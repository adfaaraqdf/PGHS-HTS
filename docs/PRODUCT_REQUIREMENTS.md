# 제품 요구사항

## 1. 문서 목적과 범위

- 상태: 0단계 기준선
- 제품: 학교 축제용 모바일 실시간 모의 주식거래 웹 서비스
- 사용자: 학교 Google 계정을 가진 학생, 권한이 부여된 관리자·운영자
- 본 문서는 **무엇을 보장해야 하는지**를 정의한다. 구현 구조는 `ARCHITECTURE.md`, 필드와 API는 `DATA_CONTRACTS.md`, 미확정 결정과 개발 기본값은 `DECISIONS.md`가 담당한다.
- 0단계에서는 문서만 작성하며 애플리케이션 코드, Firebase 리소스, 시드, 배포를 만들지 않는다.

요구사항이 충돌할 때 우선순위는 데이터 무결성·보안·장애 복구·모바일 사용성·안정성·비용 통제·운영 편의성·기능 수 순이다. 보안 또는 자산 무결성을 낮추는 방식으로 가용성을 확보하지 않는다.

## 2. 제품 목표와 성공 조건

전교생 수백 명이 축제 당일 동시에 접속해 동아리를 탐색하고, 별점을 확인하며, 가상 주식을 거래하고, ETF·자산·랭킹·속보를 모바일에서 이해할 수 있어야 한다. 실제 화폐나 실제 증권과 연결하지 않는다.

출시 승인에 필요한 상위 성공 조건은 다음과 같다.

1. 공식 종목은 `CLUB_CATALOG.md`의 22개뿐이고 별칭이 별도 종목이 되지 않는다.
2. 모든 신규 사용자는 서버의 원자적 초기화로 최초 1회만 1,000,000원을 받는다.
3. 클라이언트가 현금, 보유량, 체결가, 가격, 랭킹, 관리자 권한을 직접 결정하거나 변경할 수 없다.
4. 동시·중복 요청, 재시도, 네트워크 응답 유실에도 거래가 중복 또는 부분 반영되지 않는다.
5. 모든 동아리는 동일한 시장 초기 조건을 가지며 정확히 하나의 ETF에 속한다.
6. 공개 랭킹은 이메일, Google UID, 실명을 노출하지 않는다.
7. 핵심 기능의 Emulator 자동 테스트, Rules 테스트, 부하 테스트, 운영 리허설과 롤백 절차를 통과한다.

## 4. 기능 요구사항

### 4.1 인증과 계정

| ID | 요구사항 | 인수 기준 |
|---|---|---|
| AUTH-01 | Firebase Google Authentication을 사용하고 `ALLOWED_SCHOOL_DOMAIN`의 검증된 학교 계정만 허용한다. | 클라이언트 검사는 UX에만 쓰며 서버가 토큰, `email_verified`, 도메인을 다시 검증한다. |
| AUTH-02 | 도메인을 여러 파일에 하드코딩하지 않는다. | 실제 도메인이 환경 설정 한 곳에서 주입되며 미설정 운영 환경은 안전하게 실패한다. |
| AUTH-03 | Google UID당 사용자 문서는 하나이며 초기화는 원자적·멱등이다. | 같은 요청의 순차·동시 재호출에도 초기 자금과 문서가 한 번만 생성된다. |

| AUTH-05 | 복수 학교 계정을 가진 실제 한 사람을 완전히 식별할 수 없음을 명시한다. | 학생 명부 또는 별도 학생 식별자가 없이는 UID 단위 보장임이 운영 체크리스트에 남는다. |
| AUTH-06 | 로그아웃, 인증 유지·만료, 접근 거부, 인증 중 로딩과 재시도를 제공한다. | 허용/비허용/미인증/만료 경로가 테스트된다. |

| MKT-05 | 적은 평가 수와 오래된 평가가 가격을 과도하게 좌우하지 않는다. | 신뢰도 축소와 최신성 감쇠 규칙이 `PRICE_ENGINE.md`에 수식·예제로 정의된다. |

| MKT-07 | 가격 갱신 주기와 최대 지연은 설정·관측 가능해야 한다. | 개발 기본값과 변경 근거는 `DECISIONS.md`, 허용 지연은 `PRICE_ENGINE.md`에 기록된다. |
| RATE-01 | 기존 별점 시스템은 규격 확인 전 어댑터 경계 밖으로 추정 구현하지 않는다. | API 규격은 placeholder이며 무평가 상태가 중립 가격 신호로 처리된다. |
| RATE-02 | 학생의 '별점 평가' 활동은 기존 시스템 계약에 맞는 제출 또는 공식 이동 경로로 제공한다. | 앱 내 제출·기존 시스템 링크·조회 전용 중 운영 방식을 U-019에서 확정하며, 규격 없이 로컬 평가 저장소를 임의 생성하지 않는다. |

### 4.3 거래와 자산

| ID | 요구사항 | 인수 기준 |
|---|---|---|
| TRD-01 | 매수·매도는 인증된 callable Cloud Function에서만 체결한다. | 요청은 `clubId`, 양의 정수 `quantity`, `idempotencyKey`만 신뢰 가능한 입력 후보로 받는다. |
| TRD-02 | 서버는 계정·학교 도메인·시장·종목·가격·현금·보유량을 다시 검증한다. | 가격, 총액, 수수료, UID, 현금, 보유량, 관리자 여부, 체결 시각의 클라이언트 값은 거부/무시한다. |
| TRD-03 | 거래는 원자적이고 멱등이다. | 중복 키, 버튼 연타, 동시 거래, 재시도, 응답 유실에도 자산이 정확히 한 번만 변한다. |
| TRD-04 | 현금·가격은 원 단위 정수, 수량은 0 이상의 정수이며 체결 수량은 양의 정수다. | 음수 잔액·보유량, 소수 가격·수량, 부분 반영 경로가 없다. |
| TRD-05 | 매수 평균가는 가중 평균, 매도는 잔여 평균가 유지, 전량 매도는 정해진 방식으로 정리한다. | 반올림과 전량 매도 정책이 계약 및 테스트와 일치한다. |
| TRD-06 | 내 자산은 현금, 보유 평가액, 총자산, 보유량, 평균 매수가, 수익률을 제공한다. | 서버 기준 가격을 사용하고 로딩·오류·최신 시각을 표시한다. |

| ID | 요구사항 | 인수 기준 |
|---|---|---|

| ETF-03 | 스포츠 ETF는 `volleyball-love` 하나뿐이다. | 분산 효과가 없다는 경고가 ETF 화면과 문서에 표시된다. |
| RANK-01 | TOP 10, 내 순위, 내 총자산, 닉네임, 갱신 시각을 제공한다. | 전체 사용자를 화면 요청마다 읽지 않고 서버 집계 projection을 사용한다. |
| RANK-02 | 공개 랭킹은 이메일·UID·실명·내부 식별자를 노출하지 않는다. | 공개 항목은 닉네임, 자산, 순위, 갱신 시각으로 제한된다. |
| RANK-03 | 동점과 갱신 최대 지연 규칙이 결정적이다. | 동일 자산은 같은 경쟁 순위, 표시 순서는 비식별 보조키로 결정하며 기본 지연은 `DECISIONS.md`를 따른다. |
| NEWS-01 | 속보, 전체 공지, 종목별 최근 뉴스와 활성 호재·악재를 제공한다. | 시간 범위와 대상이 서버에서 검증되고 최신 뉴스 쿼리는 페이지/개수 제한을 가진다. |

### 4.5 관리자

관리자는 호재, 악재, 속보, 전체 공지, 시장 정지·재개, 종목별 거래 정지, 시장 초기화, 폐장 특수 설정을 수행할 수 있다(`ADM-01`). 모든 변경은 서버 권한 검증, 사유·행위자·전후 상태·서버 시각을 가진 추가 전용 감사 로그를 남긴다(`ADM-02`). 시장 초기화와 운영 배포처럼 파괴적 작업은 확인 절차, dry-run/영향 요약, 권한 분리, 백업과 롤백을 요구한다(`ADM-03`).

| ETF | 6개 ETF의 현재가, 수익률, 구성 종목, 스포츠 ETF 단일 구성 경고 |

모든 화면은 모바일 우선 다크 모드 증권 앱 스타일, 한 손 조작, 최소 약 44px 터치 영역을 따른다(`UX-01`). 상승·하락은 색상뿐 아니라 부호·아이콘·텍스트로 구분한다(`UX-02`). 로딩·빈 화면·오류·재시도·오프라인/지연 상태를 제공한다(`UX-03`). 복잡한 차트와 과도한 애니메이션은 사용하지 않는다(`UX-04`).

| NFR-COST | 쿼리 개수·limit·페이지 크기·샤드 수·스케줄 주기를 제한하고 읽기/쓰기/함수 호출량과 예산 경보를 관측한다. |

| NFR-REL | 에뮬레이터, 단위·통합·Rules·동시성·부하·모바일·운영 리허설을 거쳐야 하며 테스트를 삭제하거나 약화해 통과시키지 않는다. |
| NFR-TIME | 모든 저장 시각은 Firestore Timestamp와 서버 시각을 사용하고 표시 시간대는 `FESTIVAL_TIMEZONE` 설정을 따른다. |

## 7. 명시적 제외 범위

공매도, 옵션, 선물, 레버리지, 지정가 주문, 호가창, 복잡한 기술적 차트, 실제 화폐, 학생 간 송금, 사용자 간 주식 양도, 가상 추가 동아리, ETF 거래는 구현하지 않는다. 프런트엔드는 Vanilla HTML/CSS/JavaScript이며 React·Vue와 불필요한 대형/디자인 시스템 패키지를 추가하지 않는다.

| 동아리 로고, 대표 이미지, 부스 위치, 운영 시간 | 각각 `logoUrl`, `imageUrl`, `boothLocation`, `operatingHours`: `null` |
| 부스 번호, 축제 당일 체험 내용 | 필드를 도입한다면 각각 nullable이며 확인 전 UI에 사실처럼 표시하지 않음 |
| 학교 이메일 도메인 | 확인값 `pangyo.hs.kr`; 환경별 `ALLOWED_SCHOOL_DOMAIN`으로 주입 |
| 관리자 이메일/권한 원천 | `ADMIN_AUTHORIZATION_PLACEHOLDER` 또는 확정된 서버 권한 원천 |
| 축제 날짜, 개장·폐장 시각 | `FESTIVAL_DATE`, `MARKET_OPEN_AT`, `MARKET_CLOSE_AT` |
| 기존 별점 시스템 API 규격 | `RATING_PROVIDER_*` 설정과 미구현 어댑터 경계 |

공식 종목의 개발 기본은 `isActive: true`, `tradingStatus: "open"`이다. 미제공 값을 임의 문자열, 가짜 URL, 추정 일정, 임의 관리자 계정으로 채우지 않는다.
